# Android Platform Guide

Use this guide with the shared [production](../production.md),
[permissions](../permissions.md), [plugin adapter](../plugins.md),
[compatibility](../compatibility.md), and
[real device release checklist](../real-device-release.md) docs when preparing
an Android export.

## Build Checklist

1. Run `npm run build` so Godot exports the current `dist/app.js` bundle.
2. Run `npm run check:exports` if your app was generated by the CLI.
3. Create or update the Android export preset in official Godot.
4. Install and verify the arm64-v8a and/or x86_64 runtime target used by the
   export.
5. Enable only the permissions required by APIs your app actually uses.
6. Install and configure any native Android plugins required by registered
   `@vue-godot/device` adapters.
7. Test an exported APK/AAB on a real device or representative hosted device.

Editor play mode is not enough for Android capabilities. Permission prompts,
manifest entries, plugin loading, safe areas, virtual keyboard behavior, and
background lifecycle events need exported-device validation.

## Common Permissions

| App capability                                                                      | Android setup                                                                                            |
| ----------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `fetch()`, `WebSocket`, reachability probes                                         | `android.permission.INTERNET` where required by the export profile                                       |
| Geolocation adapters / `navigator.geolocation`                                      | `android.permission.ACCESS_FINE_LOCATION` and/or `android.permission.ACCESS_COARSE_LOCATION`             |
| Camera adapters / `getUserMedia({ video: true })` / `<CameraView>` fallback plugins | `android.permission.CAMERA`                                                                              |
| Microphone adapters / `getUserMedia({ audio: true })`                               | `android.permission.RECORD_AUDIO`                                                                        |
| Handheld vibration / `navigator.vibrate()`                                          | `android.permission.VIBRATE`                                                                             |
| Native notifications                                                                | `android.permission.POST_NOTIFICATIONS` on Android versions that require runtime notification permission |

The browser package never opens Android permission prompts on its own.
`navigator.permissions.query()` is query-only. Request runtime permissions from
your app or native plugin, then report the result through a
`PermissionAdapter` or the capability-specific adapter.

## Runtime Permission Flow

Apps that call Godot directly can use the device permission helpers:

```ts
import {
  AndroidPermissions,
  onPermissionResult,
  requestPermission,
} from '@vue-godot/device/permissions'

const subscription = onPermissionResult(({ name, granted }) => {
  console.log(`${name}: ${granted ? 'granted' : 'denied'}`)
})

requestPermission(AndroidPermissions.Camera)

// Disconnect when the screen or integration module is torn down.
subscription?.disconnect()
```

Adapters should map platform failures to capability states:

| State                     | Android example                                                                   |
| ------------------------- | --------------------------------------------------------------------------------- |
| `supported`               | Plugin loaded, manifest is configured, and runtime permission is granted.         |
| `permission-denied`       | The user denied a runtime permission or the system reports it denied.             |
| `missing-plugin`          | The required Android plugin is not installed or did not load.                     |
| `export-misconfiguration` | Manifest permissions, Gradle settings, AAR files, or plugin metadata are missing. |
| `unsupported-platform`    | The current export is not Android or the device lacks required hardware.          |

## Adapter-Backed APIs

Register Android-backed adapters before `installBrowserAPIs()` when you want
browser-shaped globals such as `navigator.geolocation`,
`navigator.mediaDevices`, or `Notification` to exist during startup.

```ts
import { installBrowserAPIs } from '@vue-godot/browser'
import { registerDeviceCapability } from '@vue-godot/device'

registerDeviceCapability({
  capability: 'geolocation',
  pluginName: 'android-location',
  getStatus() {
    return androidLocation.getStatus()
  },
  getCurrentPosition(options) {
    return androidLocation.getCurrentPosition(options)
  },
  watchPosition(onPosition, onError, options) {
    return androidLocation.watchPosition(onPosition, onError, options)
  },
  clearWatch(watchId) {
    androidLocation.clearWatch(watchId)
  },
})

installBrowserAPIs()
```

Deep links, share sheets, camera fallback capture, microphone streaming, and
native notifications are plugin-backed responsibilities. The first-party
packages define the adapter contracts and browser-shaped wrappers; the Android
plugin still owns manifest entries, Gradle setup, activity/intent handling, and
native resource lifetime.

## UI And Lifecycle Checks

- Test `<SafeAreaView>` on devices with and without cutouts.
- Test `<KeyboardAvoidingView>` with the actual soft keyboard and your target
  input fields.
- Use `onAppLifecycleEvent()` from `@vue-godot/device/system` for Android back
  requests and route them through modals, screen stacks, router history, then
  app quit confirmation.
- Confirm camera, microphone, and sensor adapters stop native resources when
  Vue screens unmount or Godot scenes exit.
- Treat network reachability as best-effort; captive portals, firewalls, and
  platform policy can still make a successful probe misleading.

## Release Smoke

For each release candidate, test at least:

- cold launch into the main scene
- `dist/app.js` plus chunk loading
- storage persistence under `user://`
- required permission prompt flows
- denied-permission behavior
- missing-plugin or disabled-plugin behavior
- back button behavior from nested screens and modals
- safe area and virtual keyboard layout
- each registered native adapter on device
