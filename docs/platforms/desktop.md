# Desktop Platform Guide

Use this guide with the shared [production](../production.md),
[permissions](../permissions.md), [plugin adapter](../plugins.md), and
[compatibility](../compatibility.md) docs when preparing Windows, macOS, or
Linux exports.

## Build Checklist

1. Run `npm run build` so the exported project includes the current Vue bundle.
2. Run `npm run check:exports` if your app was generated by the CLI.
3. Install official export templates matching the stock Godot editor version.
4. Keep the complete universal GodotJS add-on under `addons/godotjs`.
5. Create platform-specific export presets for Windows, macOS, and/or Linux.
6. Confirm `dist/app.js` and `dist/chunks/*.js` are exported with the project.
7. Launch the exported binary outside the editor on each desktop target.

Editor play mode can hide packaging issues. Always validate resource paths,
chunk loading, file access, clipboard behavior, networking, and media playback
from an exported app.

## Desktop Capability Notes

| Capability            | Desktop behavior                                                                                                          |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| Storage               | `localStorage` uses a Godot-backed `user://` file when available; `sessionStorage` is process-local.                      |
| Clipboard             | Text clipboard uses `DisplayServer`; primary selection support is platform/display-server dependent.                      |
| Networking            | `fetch()`, `WebSocket`, and reachability probes depend on network access and host firewall/proxy policy.                  |
| External URLs         | `openExternalUrl()` delegates to Godot `OS.shell_open()`.                                                                 |
| Window lifecycle      | `onAppLifecycleEvent()` maps supported `DisplayServer` window events such as focus, blur, close request, and DPI changes. |
| Camera and microphone | Core Godot APIs and plugins vary by platform; use adapter status checks before showing capture UI.                        |
| Sensors and vibration | Handheld sensors and vibration are usually unavailable on desktop; report unsupported states instead of faking data.      |

## macOS Sandboxing And Permissions

macOS exports can be sandboxed depending on your distribution target and export
settings. When sandboxing applies, file system access, network access, camera,
microphone, notifications, and Apple events can require entitlements or native
permission prompts.

Godot exposes saved sandbox folder grants through `OS.get_granted_permissions()`
where available. `@vue-godot/device/permissions` wraps that surface with
`listGrantedPermissions()` and `revokeGrantedPermissions()`. Camera,
microphone, location, and notification prompts still need platform-native code
or plugin-backed adapters that document their plist keys and entitlements.

## Native Plugins

Desktop plugins or app-specific bridges should register adapters through
`@vue-godot/device` just like mobile integrations:

```ts
import { registerDeviceCapability } from '@vue-godot/device'

registerDeviceCapability({
  capability: 'share',
  pluginName: 'desktop-share',
  getStatus() {
    return desktopShare.getStatus()
  },
  share(data) {
    return desktopShare.share(data)
  },
})
```

Prefer explicit unsupported states when a feature is not available on a target
desktop platform. That lets browser-shaped wrappers and app UI show predictable
fallbacks instead of failing with arbitrary native errors.

## UI And Input Checks

- Verify keyboard focus traversal for all forms and modal flows.
- Verify controller/gamepad focus if the app ships game UI.
- Verify mouse hover, pressed, disabled, and long-press states on
  `<Pressable>` and button-like controls.
- Check window resize behavior, DPI scaling, and fullscreen/windowed modes.
- Test media playback from `res://`, `user://`, blob URLs, data URLs, and remote
  URLs only for the sources your app supports.

## Release Smoke

For each desktop release candidate, test at least:

- cold launch outside the editor
- `dist/app.js` plus chunk loading
- local storage persistence across app restarts
- fetch/WebSocket behavior on the target network
- clipboard read/write where the app uses it
- external URL open behavior
- modal close, window close, focus, and escape/back handling
- media and asset loading from exported resources
- adapter-backed plugins in both installed and missing-plugin states
